# Fifth goal: M2.5, transport audit (verify the loss numbers before deciding on NACK or FEC)

Save this file as `docs/goals/M2.5.md`. Run it after M2 and **before** M3.

## Why this goal exists

The M2 measurements do not match back-of-envelope math, and a recovery decision should not be built on numbers that may come from a bug or a mis-modeled link:

- At 480p (about 6 fragments per P-frame) and 0.5% iid loss, a P-frame should arrive intact about 97% of the time (0.995^6). The simulation delivered 8.3% of frames.
- Keyframe requests came out at roughly 60 per minute at every loss rate from 0.5% to 5% and at every resolution. That is exactly one request per second, the backoff cap, which suggests the receiver sits in "waiting for keyframe" almost permanently instead of recovering after the first request.
- The simulated link was rate-limited to about 102% of the *average* video bitrate while a keyframe is about 8 times an average frame. A keyframe on such a link queues for hundreds of milliseconds and delays everything behind it. Real Tailscale paths have far more capacity than the video bitrate. This was an under-specified modeling choice, not a transport property.

This goal finds out which of those explanations is true, fixes what is broken, re-measures, and then produces the comparison data needed to decide between selective NACK and XOR parity FEC.

## Before you run it (human checklist)

1. M2 is merged and pushed; working tree clean on `main`.
2. No hardware needed. Loopback and simulation only.
3. Give it a generous token budget if Codex allows one. Phase 3 is the largest part.

Implement the following as simulator-side models in a separate testkit module (clearly named, for example sim::recovery_models). - NACK-key: when a keyframe has missing fragments after one RTT plus the 8 ms reorder window, the receiver requests the missing fragments (up to two rounds); the sender keeps the last keyframe's fragments for retransmission. P-frames still use keyframe-on-loss.
