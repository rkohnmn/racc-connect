# Goal M7: end-to-end viewer and input (the first working product)

Save as `docs/goals/M7.md`.

**Run after:** M4b and M6 complete, and the M6 human checks (service, lock, UAC, probe over Tailscale) reviewed and any fixes made.
**Revisit before running:** read ADR 0001 (toolkit constraints for input), `docs/ENCODE.md` (what the stream looks like), `docs/HOST.md` and the M6 human results. Decide whether pointer injection uses the virtual-desktop absolute mode or `SetCursorPos` (see M3a hardware checks); if you do not know yet, leave the prompt's "decide by measurement" text.

## Human checklist
1. Working tree clean on `main`; both Windows PCs have the host service installed and working from M6.
2. For the human tests you need both PCs on the tailnet and (ideally) a different monitor layout on each.
3. The viewer receives video on a UDP port, so Windows Firewall may block it or show an allow prompt the first time the app runs. If video never arrives while the control connection works, check this first. When allowing it, scope the rule to the app program and the Tailscale address ranges (100.64.0.0/10 and fd7a:115c:a1e0::/48) only. The agent should add the viewer-side rule to scripts/firewall-rules.ps1 (human-run) and record any prompts you saw.
4. Latency measurement needs a way to compare screens, such as a phone camera at 120 or 240 fps pointed at both displays showing a running millisecond timer.

## Prompt
~~~text
GOAL: M7. Make the product work end to end between Windows PCs: Windows hardware decode, native wgpu rendering inside the real UI, hold-then-atomic-replace display switching, cursor drawing, pause on hide, viewer-side input capture, host-side input injection, and the real core replacing the fake core in racc-app. Result: open the app on one PC, see the other PC in the device rail, pick a monitor, watch it live and control it.

COMMON.md applies in full. Read AGENTS.md (sections 2, 4.4, 4.5, 5, 6, 7), docs/UI.md, docs/SESSION.md, docs/TOPOLOGY.md, docs/HOST.md, docs/ENCODE.md, docs/CAPTURE.md, docs/IDENTITY.md and ADR 0001 first.

PREFLIGHT
Clean tree; check-all green; M4b and M6 complete; read the M6 human results in docs/HARDWARE.md and the first-run notes; stop and report if the host does not stream to racc-probe over Tailscale as verified by the human.

DEPENDENCIES AND UNSAFE
windows crate features for Media Foundation decode, input injection and raw input as needed. unsafe only in crates/decode/src/windows/ and crates/input/src/windows/ (and the app's platform input module if the toolkit needs raw OS input per ADR 0001), with SAFETY comments and RAII wrappers.

SCOPE

A. Decode (crates/decode, package racc-decode): portable Decoder trait with fake backend; Windows backend using the Media Foundation H.264 decoder with DXVA hardware decoding to NV12 D3D11 textures where available (software fallback allowed, label it in telemetry). Input: Annex B access units from the reassembler (frames are complete and ordered; keyframe flags known). Behavior: configure from the StreamReset (width, height), accept SPS and PPS in band, discard until the first IDR, handle resolution change by reconfigure or recreate (measure and record), latest-wins (if more than 2 frames are queued, drop the oldest non-key and flag need-keyframe), report decode errors to the session as DecoderError, expose decoder name for telemetry (racc-proto/telemetry DecoderKind). Output frames are NV12 GPU textures or planes the renderer can import. A CPU upload path (copy planes into a wgpu texture) is acceptable (record per-frame cost); true zero-copy interop is out of scope.

B. Render (racc-app): a VideoSurface component using the toolkit's native wgpu path from ADR 0001: NV12 to RGB shader, letterbox via racc-topology, a cursor overlay drawn from CursorShape and cursor datagram position (using the M3a cursor mapping), hold-last-frame during switching and atomic replacement when the new epoch's first keyframe has decoded (driven by the session actions ReplaceFrameAtomically and HoldLastFrame), overlays for Connecting, Paused, Reconnecting, Error and Waiting for approval, and a debug latency overlay (frame id, capture timestamp age estimate, decode time, present interval) behind a toggle. The renderer owns the frame handoff; frames never pass through the UI message bus.

C. Real core (racc-core ViewerRuntime): wire ViewerSession (M3b), VideoReceiver and ControlConn (M2), the decoder and renderer handoff, TelemetryHub (M3a), racc-identity peer discovery (M5c) and the local host agent IPC client (M6) behind the existing CoreHandle trait, using threads and bounded channels. Device list: self plus tailnet peers from racc-identity, host-capable peers marked by probing; updates when peers appear or disappear. Selecting a device connects (Hello, handshake, topology, stream); selecting a display issues SwitchMonitor through the session. SetVisible pauses and resumes video. Reconnect, backoff and overlays follow M3b. The fake core remains selectable with --fake for UI development.

D. Input capture (viewer side, crates/input and racc-app): physical key identity to USB HID usage mapping (table-driven, tested, with a documented source for each mapping and a test for every key on a standard 104-key layout plus common media and navigation keys); modifiers tracked from physical key events; mouse absolute positions via normalize_pointer on the actual rendered video rectangle (Clamp while buttons are down, Reject on hover); relative motion when the capture mode requires it; wheel in 1/120 units; send as InputEvent with current epoch and display id; suppression rules during Switching from M3b; a visible capture indicator; an always-working release hotkey (documented, for example a chord) that cannot be forwarded to the host; on focus loss, hide, disconnect or pause send release events for all pressed keys and buttons. Never log key events.

E. Input injection (host side, in the helper): Windows injection with SendInput using scancodes (KEYEVENTF_SCANCODE with correct extended-key flags) mapped from HID usage (table-driven, tested both directions where meaningful), mouse button and wheel events, relative motion, and absolute pointer positioning using racc-topology host_pixel plus EITHER the virtual-desktop absolute mode OR SetCursorPos (implement both behind a setting; decide by measuring accuracy at all four corners and center of each monitor on this PC; record the results and make the more accurate one the default). Validate every field of InputEvent again on the host (never trust the viewer), drop events with a stale epoch or display for absolute pointer motion, rate-limit input events (generous cap) to bound abuse, track pressed keys and buttons and release them on session end, pause, control loss or helper shutdown (stuck-key protection), and ignore injection requests when no authorized session is active. Injection must run on the helper's input desktop (M6); on the secure desktop it may fail: report it as a clear status, not a crash. Never block the network threads on injection.

F. Session UX details: cursor shape cache keyed by shape_id; Remote Desktop mode (keyboard and mouse capture on) versus view-only mode; fullscreen; quality selector wired to SetQuality; device offline handling; authorization approval prompt in the UI for pending peers on this machine (using the M6 IPC) with approve and reject; the allowlist view.

MEASUREMENTS (VERIFIED-RUN on this PC via loopback host-loopback or the installed service as available; human for cross-PC)
- Decode time per frame (p50, p95) per tier for the hardware and software paths; upload and render cost.
- CPU time per second and private memory for the app while viewing 720p30 and 1080p30; same for the host (from M6) for comparison.
- Display switch: time from SwitchMonitor to atomic replace on loopback, and the number of frames shown stale.
- Input path timing on loopback: time from event generation to injection call (p50, p95).
- Pointer accuracy table (corners and center of each monitor; absolute mode versus SetCursorPos).
- Glass-to-glass latency is HUMAN-PENDING (needs the camera method); provide an on-screen millisecond timer mode to make it easy.

TESTS
HID mapping table tests (round trip where applicable, uniqueness, every key listed); input suppression and release logic (reducer tests including focus loss and disconnect); injection validation and rate-limit tests with a fake injector; decoder trait and latest-wins tests with fakes; ViewerRuntime tests with a loopback host and fake decoder; an automated end-to-end test on this PC: host-loopback plus the real ViewerRuntime with the real decoder for 30 seconds, display switch, pause and resume, quality change, kill and reconnect, keyboard and pointer events into a recording fake injector (real injection only in a human-run manual test).

DOCUMENTATION
docs/VIEWER.md (decode path, render path, handoff, overlays, runtime wiring, input capture design and the release hotkey), docs/INPUT.md (HID table sources, injection design, accuracy results, stuck-key protection, rate limits), update docs/UI.md. ADRs: decoder choice and fallback, pointer injection method decision, release hotkey, input rate limits. docs/HARDWARE.md human checks (HUMAN-PENDING): two-PC session over Tailscale in both directions; every monitor on each PC (mixed DPI at 125 and 150 percent if available); corner and center clicks; typing in several applications including with non-US layouts; modifier-only and shortcut keys (Ctrl+C, Alt+Tab behavior, Win key behavior, Ctrl+Alt+Del is not supported and must be documented); mouse wheel and drag; hold keys then disconnect (no stuck keys on the host); minimize and restore the viewer window (video pauses and resumes); switch displays rapidly; measure glass-to-glass latency with the camera method for 480p, 720p and 1080p, direct versus DERP path; unplug the network cable and watch reconnect; leave it streaming for 30 minutes and record CPU, memory and any drift or leaks. Update PROGRESS.md and OPEN_QUESTIONS.md.
~~~
