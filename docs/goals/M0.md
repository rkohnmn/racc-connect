## Before you run it (human checklist) 
 
1. Create the repository folder and place these files in it: 
   - `AGENTS.md` at the repository root 
   - `docs/PROJECT_SCOPE.md` 
   - `docs/DEV_SETUP.md` 
   - this file as `docs/goals/M0.md` 
2. Install Rust with `rustup` and confirm `cargo --version` works. Optional but useful: `cargo-deny` (`cargo install cargo-deny`). 
3. Enable goals in Codex if you have not: `codex features enable goals`, then restart Codex. Check `codex --version` (the feature shipped in v0.128.0). 
4. Run Codex with the repository folder as the working directory. Use an approval mode that lets it edit files and run `cargo` and `git` inside the workspace without asking every time, but keeps actions outside the workspace gated. 
5. If your Codex version lets you set a token budget for a goal, set a modest one. This goal is small, and a tight budget is a good guard against looping. 
6. Start a git repository first (`git init`) or let the agent do it. Do not give the agent push access to any remote. 
 
## How to launch 
 
**Option A (recommended): short launcher.** Paste this single line: 
 
``` 
/goal Complete the work specified in docs/goals/M0.md. Read AGENTS.md and docs/DEV_SETUP.md first. The goal is done only when every acceptance check in docs/goals/M0.md passes with evidence, then stop. Do not start M1. 
``` 
 
**Option B: paste the full prompt** from the next section directly. 
 
Option A keeps the goal text versioned in the repo and avoids pasting a long prompt. Option B works if you prefer a self-contained paste.

## The full goal prompt 
 
~~~text 
GOAL: M0, workspace scaffold. Create a compiling Rust workspace skeleton, seed the project documentation, and establish the verification scripts that every later milestone depends on. Write no feature code. 
 
CONTEXT 
This repository is a native, low-latency remote desktop application in Rust for three machines (two Windows 10 PCs and a 2015 Intel Mac) connected by Tailscale. The authoritative documents are: 
- AGENTS.md (repository root): rules, architecture, milestones. 
- docs/PROJECT_SCOPE.md: full product scope. 
- docs/DEV_SETUP.md: verification labels, toolchain, commands. 
Read all three completely before changing anything. If AGENTS.md is missing, stop and report that you are blocked. If PROJECT_SCOPE.md or DEV_SETUP.md is missing, record that in docs/OPEN_QUESTIONS.md and continue. 
 
SCOPE OF THIS GOAL (do exactly this, nothing more) 
 
1. Git 
   - If the folder is not a git repository, run git init and make the default branch main. 
   - Add a .gitignore suitable for Rust (target/, Cargo.lock is COMMITTED because the workspace contains binaries) and common editor and OS files. 
   - Make small logical commits as you go. Never push. Never add a remote. 
 
2. Toolchain files 
   - rust-toolchain.toml pinning the exact stable Rust version installed in this environment (record the version), with components rustfmt and clippy. 
   - Do not add the Windows or macOS targets to rust-toolchain.toml. Cross-check targets are installed per DEV_SETUP.md section 2.1. 
   - rustfmt.toml only if you need non-default settings (default is preferred). 
   - deny.toml configured to reject GPL and AGPL licenses for linked dependencies and to warn on security advisories. 
 
3. Workspace 
   - Root Cargo.toml defining a workspace with members crates/*, resolver 2, edition 2021, and publish = false for all crates. Do not choose a project license (record that as an open question). 
   - IMPORTANT NAMING RULE: the directory names stay exactly as in AGENTS.md section 3, but every Cargo package name gets the prefix rd- because a package named core conflicts with Rust's built-in crate. Examples: crates/core is package rd-core, crates/proto is rd-proto, crates/host-agent is package rd-host-agent, crates/app is package rd-app. 
   - Create these crates as minimal, compiling stubs: proto, net, topology, session, telemetry, capture, encode, decode, input, clipboard, identity, core, testkit (libraries), and host-agent and app (binaries). 
   - Each library has a lib.rs containing only a crate-level doc comment stating its single responsibility (taken from AGENTS.md section 3). Each binary has a main.rs that prints its package name and version and exits. 
   - Add #![forbid(unsafe_code)] to the crates AGENTS.md section 9 says must not contain unsafe: proto, net, topology, session, telemetry. Other crates get no such attribute yet. 
   - Add NO third-party dependencies anywhere. Path dependencies between workspace crates are allowed only where the dependency direction rules below allow them, and for M0 you may add none. Do not choose an async runtime, UI toolkit, serialization library or logging library; those are decided in later milestones. 
   - Do not define traits, types, messages or protocol constants. Those belong to M1 and later. 
 
4. Dependency direction rule and its check 
   - Document this rule in docs/DEV_SETUP.md section 5 if not already present: lower crates must never depend on higher ones, and no library crate may depend on the app or host-agent crates. In particular, rd-core and everything below it must build and test with no UI crate present. 
   - Create scripts/check-layering.sh (and scripts/check-layering.ps1 equivalent) that fails if rd-app or rd-host-agent appears in the dependency tree of any library crate, using cargo metadata or cargo tree. It must pass trivially now and fail if someone later violates the rule. 
 
5. Verification scripts 
   - scripts/check-all.sh and scripts/check-all.ps1 that run, in order: cargo fmt --all -- --check, cargo clippy --workspace --all-targets -- -D warnings, cargo test --workspace, scripts/check-layering. If cargo-deny is installed, also run cargo deny check; if it is not installed, print a clear notice and continue. 
   - Scripts must exit nonzero on the first failure. 
   - Make the .sh file executable. You cannot run the .ps1 file in a non-Windows environment; mark it UNVERIFIED in the report and keep it simple (no clever logic). 
 
6. Documentation seeds (create under docs/, concise but real, not empty placeholders) 
   - docs/PROGRESS.md: sections for Environment, Milestone status table (M0 to M10), Verified, Unverified, Blocked, and a Session log. Fill in the Environment section from the environment probe in step 8 and mark M0 status honestly. 
   - docs/OPEN_QUESTIONS.md: a template plus the entries you discover. Seed it with: (a) project license not chosen, (b) project working title not chosen, (c) the exact LocalAPI access method per platform must be verified by the identity crate, (d) UI toolkit pending spike M4a. 
   - docs/HARDWARE.md: the human-only test checklist from AGENTS.md section 10.2 as unchecked checkboxes grouped by milestone (M5, M6, M7, M8, M9), plus the environment record block from DEV_SETUP.md section 9, left blank for the human. 
   - docs/PROTOCOL.md: a short stub stating that this is filled in during M1, listing the header and message names from AGENTS.md section 4 as a table of contents with no field definitions beyond what AGENTS.md already states. 
   - docs/PACKAGING.md: a short stub stating this is filled in during M10, with the signing, notarization and autostart topics from AGENTS.md as headings. 
   - docs/decisions/0000-template.md: a short ADR template (title, status, context, decision, consequences). 
   - Record these decisions as accepted ADRs, taking their content ONLY from AGENTS.md and PROJECT_SCOPE.md, not from your own opinions: 0002 package-name prefix rd- (explain the core conflict), 0003 two-process model (host-agent plus app), 0004 Windows encode via Media Foundation with OpenH264 software fallback and no x264 (GPL), 0005 control channel over TCP with video over UDP and 1200-byte maximum datagram, 0006 relaxed zero-copy policy, 0007 no application-layer encryption and Tailscale whois allowlist. 
   - Leave 0001 intentionally unused with a one-line placeholder file stating the UI toolkit ADR is pending milestone M4a. 
   - README.md at the repository root: one page covering what the project is, current status, how to run scripts/check-all, and links to the docs. Use the working title placeholder, not Discord's name or any branding. 
 
7. Reconcile references 
   - Because of the rd- package prefix, any command in AGENTS.md or docs/DEV_SETUP.md that uses a package name (for example cargo test -p proto) must be corrected to the prefixed name. Make ONLY these package-name corrections and add a one-line note in AGENTS.md pointing at ADR 0002. Do not otherwise edit AGENTS.md, PROJECT_SCOPE.md or DEV_SETUP.md. If you believe another change is needed, add it to docs/OPEN_QUESTIONS.md instead. 
   - Add one line to AGENTS.md section 13 telling agents to read docs/DEV_SETUP.md and docs/PROGRESS.md at session start, if not already stated. 
 
8. Environment probe (run and record in docs/PROGRESS.md, labeled per DEV_SETUP.md section 1) 
   - rustc --version, cargo --version, rustup target list --installed, uname -a (or the Windows equivalent). 
   - Try rustup target add x86_64-pc-windows-msvc and x86_64-apple-darwin. If installation is impossible (no network or permissions), record that. 
   - Run cargo check --workspace --target x86_64-pc-windows-msvc and cargo check --workspace --target x86_64-apple-darwin. Record pass or fail honestly. With empty stubs these should pass; if they do not, record the exact error and do not "fix" it by adding dependencies. 
   - Record whether tailscale is installed (tailscale version) or not installed. 
 
HARD CONSTRAINTS 
- Do not write feature code, protocol definitions, types, traits, tests of real behavior, or anything belonging to milestones M1 to M10. 
- Do not add third-party dependencies. Do not add network access or telemetry. 
- Do not reference Discord's name, logo or assets in any file. 
- Do not claim platform behavior you did not run. Use the verification labels from docs/DEV_SETUP.md section 1 in every status statement. 
- Do not fabricate measurements or command output. 
- Do not push, add remotes, or modify anything outside the repository folder. 
- Do not start M1, even if you finish early, and do not "improve" things outside this scope. 
 
ACCEPTANCE CHECKS (all must pass, each with evidence) 
1. cargo fmt --all -- --check exits 0. 
2. cargo clippy --workspace --all-targets -- -D warnings exits 0. 
3. cargo test --workspace exits 0. 
4. scripts/check-layering.sh exits 0, and you demonstrated it fails correctly by temporarily adding a forbidden dependency edge, observing the failure, and reverting it. State that you did this and confirm the revert (git status clean of that change). 
5. scripts/check-all.sh exits 0 end to end. 
6. Every directory under crates/ is a workspace member with package name prefixed rd-, verified with cargo metadata output summarized in your report. 
7. grep confirms no third-party dependencies: every [dependencies] section in every Cargo.toml is empty or contains only workspace path entries (there should be none in M0). 
8. #![forbid(unsafe_code)] is present in rd-proto, rd-net, rd-topology, rd-session and rd-telemetry. 
9. All files listed in section 6 exist and are non-trivial, and README.md exists. 
10. docs/PROGRESS.md contains the Environment section with real recorded values and an honest M0 status. 
11. The cross-check results for the Windows and macOS targets are recorded in docs/PROGRESS.md with a label (COMPILE-ONLY if they passed, UNVERIFIED with the exact error if they could not run). 
12. Git history exists with small logical commits and nothing is pushed. 
 
STOP CONDITIONS 
- Stop immediately after all acceptance checks pass and the final report is written. Do not continue into M1. 
- If the same check fails three times for the same reason, stop, record the cause and what you tried in docs/OPEN_QUESTIONS.md, and report that you are blocked. Do not loop. 
- If a requirement in this prompt conflicts with AGENTS.md, follow AGENTS.md, record the conflict in docs/OPEN_QUESTIONS.md, and continue with unblocked work. 
- If you are uncertain about any requirement, record the question instead of guessing. 
 
FINAL REPORT (write it as the last section of docs/PROGRESS.md session log and as your final message) 
- A numbered list of the 12 acceptance checks, each marked PASS or FAIL with the exact command and a short excerpt of its output as evidence. 
- A list of everything you created or changed. 
- A list of anything labeled UNVERIFIED or COMPILE-ONLY and why (the .ps1 scripts will be UNVERIFIED unless you ran them on Windows). 
- A list of open questions you added. 
- A one-paragraph statement of what M1 will start from, without starting it.
~~~ 

## What to check after it finishes (human, about 10 minutes) 
 
1. Run `scripts/check-all.sh` yourself and confirm it passes on your machine. 
2. Open `docs/PROGRESS.md` and confirm every claim has a verification label and no invented numbers. 
3. Run `git log --oneline` and confirm small, sensible commits with no remote. 
4. Skim `AGENTS.md` with `git diff` to confirm the only edits were the package-name corrections and the single session-start line. 
5. On a Windows PC, run `scripts/check-all.ps1` once. It was likely never executed by the agent, so any bug is yours to catch now. 
6. Fill in the environment record block in `docs/HARDWARE.md`: GPUs, Mac model, macOS version. 
7. Answer the seeded open questions that matter (project name, license) or defer them deliberately. 
 
If everything passes, the next goal is M1 (the `rd-proto` crate).
